# Out of the Box — externality & composability threat modeling

Generate concrete, ranked attack hypotheses that live outside the audited contracts: external capital, markets, oracles, integrated protocols, actors, and timing. Ground every hypothesis in a specific assumption the code makes about the outside world, then challenge it.

## When to use

- During any audit/review, after understanding intended behavior, in parallel with line-by-line bug hunting.
- Highest yield when the protocol: reads prices/rates/exchange-rates; integrates DEXes, lending markets, vaults, bridges, or wrappers; accepts tokens it doesn't control; relies on keepers/relayers/admins/oracles; distributes rewards/fees; has time-delayed, queued, or multi-step flows; or is about to deploy/migrate/launch.
- Answers: What external systems can influence this protocol? Which assumptions fail under composition? What external capital/liquidity/assets/actors/market conditions can an attacker use? Can locally correct code be system-unsafe?

## Mental model — 10 rules

1. **Capital is not a security parameter.** Any check satisfiable with one-block borrowed capital is not a check. First analyze every gate against infinite temporary capital, then against funded multi-block capital.
2. **The protocol is its own exit liquidity.** The dominant real-world loss mode is borrowing real assets against manipulated value and defaulting (bad debt) — not withdrawing the manipulated asset.
3. **Ambient MEV is a counterparty with a ~1-block SLA.** Any profitable state error is harvested by bots; they also frontrun/poach exploits. "Arbitrageurs will correct it" is not a defense.
4. **Rational inaction breaks protocols.** Liquidators/keepers/arbitrageurs act only when paid. Incentive ≤ 0 means the safety mechanism silently does not exist — solvency fails with no attacker at all.
5. **Every external system is adversarial or broken.** Oracles lie or stall, tokens misbehave, partners get compromised or spoofed, chains reorg, sequencers halt, admins fat-finger.
6. **Time is attack surface.** Every window — check→effect, request→finalize, epoch end→tally, deploy→first use — is exploitable. The deployment/initialization window is the kill zone.
7. **Failure/retry/migration paths are weaker than happy paths.** Budget review time by "what happens when the external call fails", not by call frequency.
8. **Mitigations create their own attack surface.** Test every defense under the exact attack it was built for (flash-loan guards, sanity bounds, min-shares, caps, TWAPs).
9. **Loss ≠ profit.** Size impact by protocol exposure, not attacker gain — illiquid exits cap profit, not damage. No-profit griefing and exit-path DoS still rate high when assets are volatile.
10. **Forks inherit known exploits.** The same bug iterates across forks (empty-market, read-only reentrancy). If it was exploited anywhere, test it here — including out-of-scope adapters, oracle contracts, and post-audit diffs.

## Taxonomy map

- **A. Price-source manipulation** — reading manipulable market state as truth.
- **B. Oracle integrity & liveness** — writing, freshness, and config of price data.
- **C. Peg, unit & derivative assumptions** — hardcoded equivalences and denomination errors at boundaries.
- **D. Share & balance accounting vs token reality** — balances and shares diverging from internal ledgers.
- **E. External capital & thresholds** — temporary or funded capital defeating economic gates.
- **F. Timing, ordering & multi-step windows** — mempool, MEV, and every gap between check and effect.
- **G. Cross-protocol & integration trust** — calls, approvals, registries, bridges, and partners lying or failing.
- **H. Economic incentives & solvency** — rational actors (or their absence) breaking the mechanism.
- **I. Governance & operational lifecycle** — voting power, config, privileged roles, deploy/upgrade windows.

Pattern cards below: *Challenge* = assumption to attack, *Signals* = relevance triggers, *Ask* = audit questions, *Test* = generic attack path. Representative AuditVault issues per pattern: `references/auditvault-evidence.md`. Real-world exploit archetypes: `references/exploit-playbooks.md`.

## A. Price-source manipulation

- **spot-as-oracle** — *Challenge*: current pool state ≈ fair price. *Signals*: `slot0`/`getReserves`/`get_virtual_price`/`balanceOf` ratios/LP-valued-at-tick feeding mint, redeem, borrow, liquidate, rebalance; public action callable at the manipulated moment. *Ask*: cheapest price move vs extractable payout? Same pool = venue + source? Does the lowest-TVL source move the aggregate? *Test*: flash-swap skew → call the permissionless value action → restore, one tx.
- **pool-selection-abuse** — *Challenge*: the pool we read is the deep, canonical one. *Signals*: fee-tier config tables, user-supplied pool addresses, LP NFTs as collateral without whitelist/TVL floor, permissionless pool creation/init. *Ask*: who chose this pool; can a competing one exist? Can it be front-run-initialized at an extreme price? *Test*: create/select a thin pool → inflate position value → borrow/swap against it.
- **twap-window-gaming** — *Challenge*: time-averaging = manipulation-resistant. *Signals*: window < ~30 min, single-pair source, observation cadence near block time, updater liveness assumed, freshness short-circuits returning spot. *Ask*: how many observations per window? Can update txs be censored/delayed economically? Longest tolerable staleness? *Test*: hold the skew for exactly the window with funded capital; or starve updates, then bundle trade+update in one tx.
- **weakest-source-aggregation** — *Challenge*: N sources = N-source security. *Signals*: min/max/median over source arrays with per-source fallbacks, unsorted "median", view-only unvalidated price paths, circuit breaker updated and consumed in one tx. *Ask*: cost to control the cheapest single source? Is the median actually sorted? Any unvalidated read path reachable? *Test*: manipulate the cheapest leg → the aggregate moves.
- **lp-mechanics-side-channel** — *Challenge*: only `swap()` moves price. *Signals*: single-sided adds that rebalance, asymmetric add+withdraw, hooks with automatic swaps, passive orders rebuilt per-tx from oracle price. *Ask*: which LP path equals a swap without its fee/impact? Can the same account be trigger and fee beneficiary? *Test*: use add/remove as a price-impact-free swap; split one swap to re-hit best passive orders.
- **read-only-reentrancy** — *Challenge*: view getters are always consistent. *Signals*: price getter without reentrancy guard, state updated after external calls, LP collateral from pools with native-asset/token callbacks. *Ask*: any path where the getter returns mid-update state? Which integrators read it in the same tx? *Test*: remove liquidity → inside the callback re-read the victim's price → borrow/liquidate on the stale value.

## B. Oracle integrity & liveness

- **oracle-write-abuse** — *Challenge*: only honest, expected actors write prices. *Signals*: permissionless `submitValue`/update, small-N quorums, duplicate/unregistered signers, caller-controlled update timestamps, unverified forwarders. *Ask*: cost of a fake write vs value it unlocks? Can one entity satisfy the quorum? Who can trigger updates, when, how often? *Test*: write the price → consume it in the same tx (borrow, liquidate, mint).
- **staleness-heartbeat-mismatch** — *Challenge*: feeds update uniformly and never fail. *Signals*: one staleness constant across mixed heartbeats, missing `updatedAt`/`price>0`/bounds checks, all-market NAV loops that revert on one feed. *Ask*: real heartbeat per asset vs config? Blast radius if the least important feed halts? Degraded mode? *Test*: stale one feed → deposits/withdrawals/liquidations DoS protocol-wide.
- **stale-cached-reads** — *Challenge*: stored value = current value. *Signals*: Stored/Current read pairs, accrual/refresh present in some paths and missing in others, replayable old messages, per-chain price caches. *Ask*: which functions act on price-dependent state without syncing first? Can an old message ever be (re)delivered? *Test*: let time/rates move → call the non-syncing path (mint, refund, margin check).
- **pull-oracle-multi-price** — *Challenge*: one canonical price per tx. *Signals*: permissionless `updatePriceFeeds` mid-flow, pricing from "most recently stored", no per-tx pinning, block timestamp coarser than oracle update frequency. *Ask*: can two valid signed prices be live in one block? Are deposit and withdraw priced from the same pinned version? *Test*: update low → deposit → update high → withdraw, one tx, flash-magnified.
- **oracle-misconfig-harvest** — *Challenge*: wrong parameters get noticed before exploitation. *Signals*: hand-assembled adapter math (ratio × price), governance-set oracle params, caps/floors on exchange rates, LST priced as underlying. *Ask*: sanity bound vs a second source? Can pause execute faster than bots (minutes)? Config changes simulated against live positions? *Test*: compute the first-block arbitrage/liquidations after a bad parameter lands — bots need no capital and no hesitation.
- **price-triggered-timing** — *Challenge*: prices move smoothly through triggers. *Signals*: strict straddle checks (`primary <= trigger <= secondary`), editable pending orders, liquidator-chosen oracle versions, mismatched timestamp keys. *Ask*: what executes when price gaps through the trigger? Can the request change in the execution slot? Can liquidation increase exposure? *Test*: gap the price past the trigger → stop-loss never fires; edit the pending order after seeing the update.

## C. Peg, unit & derivative assumptions

- **hardcoded-peg** — *Challenge*: pegged/wrapped asset = underlying value, always. *Signals*: `price = 1` literals, `minOut == amountIn` on stable swaps, expired-derivative → 1:1 branches, no depeg circuit breaker, min/max answer bounds. *Ask*: solvency if this trades at 0.95 — or at 0.10 while a floor says 1.0? What is it worth in a forced exit today, via real venues? *Test*: acquire the depegged asset cheap → deposit/mint at par → borrow/redeem → default.
- **stable-basket-tolerance-arb** — *Challenge*: whitelisted stables are interchangeable at $1. *Signals*: oracle-priced mint + asset-choice redemption, `priceTolerance` exceeding total round-trip fees, fees paid in the liability token. *Ask*: is mint→redeem profitable at the band edge? What backs accumulated fee balances? After N repetitions? *Test*: mint with the rich stable → redeem into the cheap one → repeat each deviation.
- **derivative-mispricing** — *Challenge*: LP/PT/LST rates are static, 1:1, or of fixed composition. *Signals*: hardcoded multipliers, assumed token indexes/order, `min(constituents) × rate` heuristics, deployment-time parity constants. *Ask*: does the rate drift (fees, rewards, maturity)? Is assumed composition true for every deployed pool of this type? Redeemable for what, at maturity, through which path? *Test*: find the instrument whose live rate diverges from the assumed rate → over/under-valued collateral → over-borrow.
- **unit-boundary-errors** — *Challenge*: all amounts arrive in the expected unit, decimals, and orientation. *Signals*: mixed 6/8/18 decimals, hardcoded `1e18` next to `decimals()`, mul-vs-div asymmetry between deposit and redeem, signed exponent casts, inverted feeds in composites, cross-chain amount fields, share-price values used as token amounts. *Ask*: unit and base/quote orientation of each operand — verified on-chain? Survives price < 1 and asymmetric decimals? Where does the intermediate overflow? *Test*: compute conversions for extreme decimals/prices; verify deposit is the exact inverse of redeem. No manipulation needed — ordinary usage misprices; this class is deterministic and often critical.

## D. Share & balance accounting vs token reality

- **donation-share-inflation** — *Challenge*: `balanceOf(this)` changes only via deposits; the first depositor is benign. *Signals*: `totalAssets()`/`exchangeRate` reading raw balances, no dead shares/virtual offset, factory-created empty markets, permissionless donate/report/`addReward` paths, caps enforced on mint but not on transfers. *Ask*: can anyone move the balance without minting shares? Is the first deposit atomic with deployment? Minimum attack donation vs expected early deposits? *Test*: mint 1 share → donate to inflate price-per-share → victims' deposits round to ~0 → redeem. Variants: inflate a rate an external lender reads; donate into fee/exchange-rate math.
- **raw-balance-vs-ledger** — *Challenge*: contract balance = accounted, distributable funds. *Signals*: `balanceOf` in share/threshold/excess math without subtracting pending liabilities, reward token == deposit token, force-sent native (selfdestruct), skim/sweep/recover functions. *Ask*: which parts of the balance are already owed, pending, or parked mid-callback? Can a 1-wei donation + `sync()` break `quote()`-dependent flows? *Test*: direct-transfer → observe mispricing, double-counted "excess", bricked migration, or payment with the contract's own money.
- **token-mechanics-conflict** — *Challenge*: tokens behave like plain ERC20. *Signals*: fee-on-transfer (credit = param, not balance delta), rebasing/elastic supply (cached ledgers, no skim path), transfer/mint hooks and callbacks (state written after the call), blacklists/zero-transfer reverts/missing `bool` returns (shared push loops). *Ask*: credited = `balanceAfter - balanceBefore`? Can balances change without a transfer event? Which accepted tokens execute user code on send/receive/mint? Can one reverting receiver block a whole queue? *Test*: deposit a taxed token; rebase between cache and withdrawal; reenter via callback; place a reverting/blacklisted receiver at the queue head.
- **rounding-dust-denominators** — *Challenge*: rounding is cosmetic; denominators are meaningful. *Signals*: conversions without explicit rounding direction, `total == 0 ?` ternaries in share math, per-user rounding-up vs global totals, low-decimal high-value assets. *Ask*: does every user-facing conversion round against the user? Can a total reach ~0 while share supply stays large? USD value of one unit of truncation for the lowest-decimal token? *Test*: grind a total to 1 wei (redeem-all-but-1) → next mint/borrow prices off the near-zero base → unbacked value; or spam 1-wei mints across accounts.
- **one-directional-accounting** — *Challenge*: value only goes up. *Signals*: `if (total > lastTotal)` with no `else`, revenue snapshots never clawed back, loss loops mutating the denominator mid-loop, rebase mechanisms without a slashing path. *Ask*: exact code path when the underlying loses value — who absorbs it, in what order? Can booked revenue be reversed by later losses? *Test*: underlying loses 20% (slash, negative rebase, strategy loss) → check withdrawals, solvency, and late reverts.
- **unclaimed-yield-sandwich** — *Challenge*: share price captures all shareholder value. *Signals*: `totalAssets()` = `balanceOf` of a strategy farming externally, public `harvest`, no per-deposit reward checkpointing. *Ask*: does the price include claimable-but-unharvested rewards? Can deposit→harvest→withdraw happen in one tx? Are rewards vested/streamed? *Test*: enter right before the harvest, exit right after — capture yield risk-free.

## E. External capital & thresholds

- **temporary-capital-thresholds** — *Challenge*: holding a balance for one block = economic commitment. *Signals*: `balanceOf ≥ threshold` gates, deposit and withdraw in the same block, permissionless `checkpoint()`, quorum/weight from current totals, no historical snapshot. *Ask*: cheapest way to satisfy this check for exactly one block? Atomic deposit→act→withdraw? Is power snapshotted before the proposal exists? What changes when a lending market for this token launches? *Test*: flash-borrow → pass the gate (vote, gauge weight, reward calibration, withdrawal) → unwind.
- **flash-callback-unbound** — *Challenge*: `msg.sender == provider` proves we initiated the loan. *Signals*: `receiveFlashLoan`/`onFlashLoan` with a single caller check, no operation-id binding callback to an initiator flow, unverified ERC3156 `initiator`. *Ask*: can a third party trigger this callback with arbitrary params, mutating whose state? *Test*: order the provider to call the victim's callback with crafted `userData` → force actions on others' positions.
- **funded-persistent-manipulation** — *Challenge*: manipulating long enough costs more than it pays; TWAP/multi-block reads save us. *Signals*: low-cap/low-volume collateral (especially the protocol's own token), shallow oracle sources, no borrow caps relative to manipulation cost, insurance fund bearing tail risk. *Ask*: cost to 10–100× each collateral's price across the oracle's sampling window vs pool borrow liquidity? Can one entity amass most of the collateral supply? *Test*: multi-block/multi-week price hold with own capital, optionally suppressing arbitrage → borrow everything → default.
- **self-liquidation-weaponization** — *Challenge*: position owner and liquidator are economically distinct; global health modes can't be forced. *Signals*: `owner != msg.sender` as the only guard, recovery modes driven by user-movable aggregates, liquidation bonus paid from lender principal, asymmetric pausing (repay paused, liquidation open). *Ask*: create→borrow→seize in one tx? Can one actor force the global mode? Is the guard proxy-proof? *Test*: flash-open a maxed position → push it (or the system) over the threshold → self-liquidate via proxy → pocket the bonus, socialize the shortfall.
- **jit-distribution-capture** — *Challenge*: eligibility at distribution time ≈ risk borne over the accrual period. *Signals*: pro-rata rewards/fees/penalties to current LPs/stakers at a specific block, predictable value-accruing transactions, penalty accounting resettable by tiny side operations. *Ask*: who can be 99% of the eligible set for exactly one block? Can the measurement be reset via a side path first? *Test*: inject dominant liquidity/stake just before the distribution → remove it just after.

## F. Timing, ordering & multi-step windows

- **missing-real-slippage** — *Challenge*: an in-tx quoted `minOut` protects the trade. *Signals*: literal `0` min-out, minOut computed from the executing pool's own views, `deadline = block.timestamp`, permissionless swaps of protocol/user funds, permit-based swaps with user-controlled slippage. *Ask*: who chooses minOut, from what price source — movable in the same block? *Test*: sandwich the protocol-internal swap (redemption, reserve sale, vault unwind).
- **permissionless-claim-frontrun** — *Challenge*: the legitimate actor's tx lands first. *Signals*: unauthenticated `initialize`/register/first-claim of a scarce slot, CREATE2/PDA derivation from unauthenticated seeds, a second creation path that skips bookkeeping. *Ask*: can anyone call this first with the same params? Is the seed/salt authenticated? *Test*: frontrun the registration/init; pre-create the pair/pool at the predicted address and own its initial state.
- **mempool-auth-replay** — *Challenge*: a valid signature/payload/proof ⇒ the rightful submitter. *Signals*: digest missing caller/nonce/deadline/chainid/permission-id, payout to `msg.sender` after permissionless verification, permits without witness binding. *Ask*: can an observer steal the outcome — or burn the payload to DoS the honest tx? *Test*: copy the payload from the mempool → frontrun with own recipient; or consume the nonce/signature first.
- **liquidation-evasion** — *Challenge*: liquidatable ⇒ will be liquidated. *Signals*: status re-checks at execution time, transferable positions without health checks, liquidator preconditions on their own balance/composition, owner-controlled inputs to liquidation math. *Ask*: what can the owner (or anyone) do in the same block to make this liquidation revert — for dust? *Test*: 1-wei self-action, dust-donation to the liquidator, or position transfer to invalidate the call → bad debt accrues.
- **onbehalf-griefing** — *Challenge*: acting on someone's behalf is always beneficial to them. *Signals*: `depositFor`/`stakeFor`/receiver params, third-party-writable per-user cooldowns/arrays/timestamps, request/complete flows where `complete` runs standalone. *Ask*: can a stranger reset my timelock, extend my lock, move my epoch/index, or force-initialize my withdrawal — for dust? *Test*: 1-wei on-behalf action → victim's withdrawal blocked, queue wedged, or settlement desynced.
- **epoch-boundary-drift** — *Challenge*: inputs freeze when the epoch ends. *Signals*: tallies reading live balances/weights for past epochs, batched multi-tx finalization, entities creatable with past effective dates, parent/child contracts using different snapshot sources. *Ask*: between epoch end and finalize, what state can still change? Is power snapshotted at epoch end or read at tally? *Test*: move balances/votes/gauges inside the window; create a retroactive entity; double-count across batches.
- **two-step-completion** — *Challenge*: whoever finishes a flow is whoever started it. *Signals*: phase-2 permissionless, keyed by (pool, receiver) not sender; intermediate contracts without sender binding; multiple entry points to the same state (async + sync paths). *Ask*: who can trigger the finalizing message, with whose parameters? Do all paths revoke the same claims? *Test*: supply the dust second leg with attacker-chosen slippage/params; complete the victim's flow badly.
- **cross-system-toctou** — *Challenge*: external state verified at check time still holds at effect time. *Signals*: external deposits/registries/expiry sweeps, first-seen credentials trusted, dispute windows exceeding the environment's data-retention limit (e.g. 256-block `blockhash`), off-chain watchers as the only defense. *Ask*: what can the external system change between my check and my effect? Does my proof window fit the data-availability limit? If the watcher crashes, who notices? *Test*: frontrun the external deposit/registry write; let the evidence expire; act after the state lapses.
- **chain-liveness-abuse** — *Challenge*: time-critical txs land; chain components agree on ordering. *Signals*: fixed-fee tx types exempt from congestion pricing, missing fraud-proof stubs, sequencer-down handling absent, low-confirmation randomness/oracle reads on reorg-prone chains, txpool-vs-validator ordering mismatches. *Ask*: which flows die if blocks are full for an hour or the sequencer is down for a day? Is every tx type congestion-priced? *Test*: crowd out liquidations/top-ups; exploit the stale-price window after sequencer downtime; double-spend via reorg; craft always-rejected blocks.
- **cooldown-penalty-bypass** — *Challenge*: one cooldown per account covers the whole balance; the penalized fast exit never undercuts the penalized slow exit. *Signals*: single `cooldownStart` per account with partial unstakes, fixed-penalty early exit coexisting with variable slashing, delays keyed to a user-controlled identifier. *Ask*: is the cooldown per-amount or per-account? Which is worse for the user: fixed early-exit penalty or the pending slash? Can the window be reset by choosing a fresh key? *Test*: season the whole balance with a 1-token unstake; exit early to dodge a larger pending penalty.

## G. Cross-protocol & integration trust

- **arbitrary-callee** — *Challenge*: callers pass honest, well-known contracts. *Signals*: user-controlled `to.call(data)` from fund-holding contracts, caller-supplied authority/registry contracts, approve-then-call routers, user-chosen wrapper/token addresses. *Ask*: can any user influence target/calldata of a call made with protocol funds/approvals/NFTs? Is the callee allowlisted on-chain? *Test*: point the call at an attacker contract — or at a victim token's `transferFrom` using the protocol's standing approval.
- **approval-proxy-drain** — *Challenge*: only the approver initiates spends through this helper. *Signals*: `transferFrom(owner, …)` with `owner` as free calldata, helper/router contracts users must approve, accounting that debits `msg.sender` instead of `owner`. *Ask*: is every `from`/`owner` bound to `msg.sender` or a signature? Are approvals for feature A reusable by feature B? *Test*: call the helper with the victim's address → spend their allowance.
- **partner-registry-abuse** — *Challenge*: implementing the interface ⇒ genuine instance of the partner protocol. *Signals*: market/gauge/pool/pair addresses as calldata without factory checks, CREATE2 same-address-everywhere tokens, batch ops on unvalidated pairs. *Ask*: is the address checked against the canonical registry (`isPair`/`isGauge`/`isMarket`)? Can it be pre-deployed at this address on another chain? Can it re-enter or lie about balances? *Test*: deploy a fake partner → integrate → inflate balances/rewards → drain.
- **third-party-mechanics-misread** — *Challenge*: the external protocol behaves like our simplified model (and our mocks). *Signals*: mocks standing in for dependencies, no mainnet-fork tests, calls into external reward/staking/CDP systems, "works in tests" comments. *Ask*: does the external call mutate their state (auto-stake, claim-for-all, cooldown)? Which external event — liquidation, cliff, governance change, upgrade — breaks our flow? *Test*: fork-test against the real deployed contracts; enumerate their state changes that invalidate ours.
- **failure-retry-paths** — *Challenge*: retry/recovery/compose paths need less validation than first delivery. *Signals*: `failedMessages` stores, retry/recall/manual-compose entrypoints, try/catch leaving approvals or state behind, two-tx compose windows, "admin recovery" functions. *Ask*: is the retry callable by anyone, re-applying every first-pass check? Is the message consumed before re-execution? Between delivery and composed execution, who can act on the delivered funds? *Test*: reuse a failed message; front-run the compose; redirect the recovery.
- **bridge-endpoint-divergence** — *Challenge*: the other chain's endpoint interprets my message exactly as I encode it. *Signals*: duplicated L1/L2 validation logic, hand-encoded calldata, per-chain token order/decimals, one-way-supported token types, unsynchronized upgrades. *Ask*: is every validity interval on side A accepted on side B (test boundary values)? Is calldata built type-safely against the destination? Can anything be bridged that can't bridge back? *Test*: bridge boundary/edge parameters; bridge the one-way token → funds locked on both sides.
- **crosschain-identity** — *Challenge*: same address = same entity on every chain. *Signals*: `refundAddress: msg.sender`, missing L1→L2 alias un-mapping, relayer contexts returning the relayer as sender, CREATE-factory addresses reused on new chains. *Ask*: who controls this exact address on every chain that receives funds — verified on-chain? Is `msg.sender` the user or the forwarder? *Test*: route funds/refunds to a chain where the address is uncontrolled or attacker-grindable.
- **messaging-fee-mismatch** — *Challenge*: cross-chain calls behave like local calls — atomic, cost settled locally. *Signals*: destination gas prepaid at source, hardcoded gas constants, `payable` bridge entrypoints without `msg.value` reconciliation, missing refund paths, user-specified destination gas. *Ask*: who pays destination gas, with what enforced min/max? What happens to excess value on success paths? Can a too-cheap message wedge the channel for everyone behind it? *Test*: underpay/under-gas a message → channel halts in STORED state; excess fees strand or subsidize.
- **collateral-legitimacy** — *Challenge*: an asset presented under a trusted ticker/message is backed and canonical. *Signals*: cross-chain collateral/mint messages, permissioned listing of new collateral, pricing of assets whose backing lives in another protocol, fallbacks accepting arbitrary token contracts. *Ask*: for each collateral, who vouches it exists and is backed — and what if that voucher is compromised or socially engineered? Is there a supply/conservation check between representation and escrow? *Test*: counterfeit listing, zero-value bridge deposit, or upstream insolvency → borrow/mint against the phantom.
- **privileged-external-actor** — *Challenge*: the small set of external key-holders/operators is honest and uncompromised. *Signals*: low-threshold multisigs over bridge vaults, single minter of wrapped assets, entrypoints assuming a specific offchain caller (missing `onlyRelayer`/`onlyKeeper`), proposer/relayer-supplied data trusted without content checks, trusted offchain components (bridge server, prover, API partner), upgrade keys = operational keys. *Ask*: maximum damage if each single key/role/partner is compromised? Are operator claims bound on-chain to verifiable external facts? Can one validator's passive non-compliance wedge the pipeline? *Test*: model compromise of each external actor; call the "trusted" entrypoint as anyone; verify on-chain invariants cap the blast radius.

## H. Economic incentives & solvency

- **liquidation-incentive-failure** — *Challenge*: liquidators always show up; the bonus never threatens solvency. *Signals*: fixed-% bonus, bonus flooring to 0 when underwater, bonus paid from reserves/user collateral, keeperless design. *Ask*: who liquidates a deeply underwater position — is the bonus still ≥ gas + risk? Do successive liquidations compound insolvency? *Test*: crash the collateral price; check both branches — no liquidator (bad debt piles up) and liquidation-deepens-insolvency.
- **liquidation-denial-lock** — *Challenge*: any underwater position can always be liquidated; auctions always terminate. *Signals*: user-controlled price inputs to liquidation math, boundary `>` vs `>=` conditions, dust orders blocking backstop books, one reverting token in the collateral list. *Ask*: can the owner or a griefer make liquidation unexecutable, cheaply? Can an auction end filled but unterminatable? *Test*: extreme price set, 100% bid, dust at the tick boundary, reverting transfer → bad debt accrues.
- **liquidator-solvency-unchecked** — *Challenge*: the liquidator actually pays; absorbing liabilities is safe. *Signals*: no post-trade risk check on the bidder, callbacks executed before risk checks, self-fill allowed. *Ask*: is the bidder risk-checked after execution? Can liquidation run reentrantly before the triggering action's risk check? *Test*: bid without funds (balance goes negative = printing money); shuffle liabilities to a shell account.
- **reward-accrual-replay** — *Challenge*: claim/accrue functions are idempotent. *Signals*: `poke`/`accrue`/`claim` callable unlimited times per epoch, zero-value transfers triggering settlement, "claimable" ignoring claimed state, rewards on cached stake pending external confirmation. *Ask*: what stops N calls per epoch? Does a zero-amount operation trigger settlement? *Test*: spam the free trigger → drain the shared reward budget.
- **fee-bypass-path** — *Challenge*: every economically equivalent flow passes the fee checkpoint. *Signals*: fee = min/max of independently zeroable quantities, multi-step exits (settle→burn), user-chosen fee token/executor, collected fees left inside rate computations, user-set gas prices for metered work. *Ask*: enumerate every sequence reaching the same terminal state — does each pay? *Test*: settle the legs in the fee-evading order; pay in a worthless token; clone the executor without the fee.
- **value-misdirection** — *Challenge*: the payer/payee mapping in code matches economic intent. *Signals*: transfers from a shared contract balance instead of the operation's party, identity (`token()`/`owner()`) queried on untrusted contracts, refunds to a default party when payment was sponsored. *Ask*: whose balance funds each outbound transfer? Can identity-bearing address params be spoofed by a lookalike contract? *Test*: trigger the operation → the fee/refund is paid from unrelated parties' funds.
- **unenforceable-slashing** — *Challenge*: bonded stake ≥ max slash at punishment time. *Signals*: sufficiency checked only at registration, governance changing minimums post-election, the offender inside the redistribution set, slash loops DoS-able by the target. *Ask*: is bond sufficiency re-checked at election and at slash time? Can governance strand existing validators below the minimum? *Test*: deplete the bond → misbehave → slash reverts or is unexecutable.
- **self-referential-feedback** — *Challenge*: prices used in solvency checks are exogenous. *Signals*: unrealized PnL credited as margin, rewards/valuations derived from user-settable price/volume, buyout functions missing active-auction checks. *Ask*: can a user's own trades move the price that checks their margin, in the same epoch? *Test*: iterative self-trades → PnL credited → fund the next order → withdraw the multiplied balance.
- **loss-socialization-runs** — *Challenge*: orderly exit for everyone. *Signals*: pending redemptions kept in totals, early exiters paid by remainers, emergency-withdraw paths with payout bugs, yield accruing to the wrong cohort during transitions. *Ask*: who pays the early exiters? What do the last withdrawers find? *Test*: simulate an exit wave — ordering determines who is made whole; check last-out solvency and bank-run amplifiers.

## I. Governance & operational lifecycle

- **external-voting-power** — *Challenge*: voting power = committed stake. *Signals*: live `balanceOf` in tallies (no snapshot), a lending market for the governance token (or one appearing), delegation loops, lockup ≤ voting period, quorum from current totals. *Ask*: can power be flash-borrowed or rented for one vote? Can the same tokens vote twice? Can a misbehaving operator unstake before enforcement lands (exit latency < enforcement latency)? *Test*: borrow → vote/delegate → unwind; verify lockups strictly exceed vote + execution delay.
- **vote-bookkeeping** — *Challenge*: counters stay valid across re-votes and voter-set changes. *Signals*: bare integer approval counters, `++` before netting the previous vote, unauthenticated vote-carry/reset helpers, small operator quorums. *Ask*: double-count on re-vote? Are pending approvals invalidated when the signer set changes? *Test*: re-vote the same option; reconfigure the owner set; carry another entity's vote.
- **proposal-liveness** — *Challenge*: approved ⇒ executable; proposing has non-zero cost. *Signals*: unbounded action arrays in `queue`/`execute`, thresholds derivable from a zero total, shared rate budgets/threads consumed before authorization. *Ask*: hard cap on proposal actions? Minimum cost to propose when the system is empty? Is auth checked before shared resources? *Test*: wedge execution with gas; spam proposals; starve consensus traffic.
- **config-bounds** — *Challenge*: privileged setters only ever receive sane values. *Signals*: no range checks on liveness-gating params, interdependent timing params set by different functions, oracle wiring set by governance, gas stipends derived from storage. *Ask*: for each setter, what value bricks the system — and can the recovery tx itself still execute? Which cross-parameter invariants exist, and are they enforced on-chain? *Test*: set extreme values (quorum > 100%, reserve too high to execute the fix); check recovery.
- **privileged-race-users** — *Challenge*: routine privileged ops can't change pending user entitlements. *Signals*: admin claims between an event and user claims, operator fees co-mingled in `totalAssets()`, cap/removal setters that skip queue updates. *Ask*: between the state-changing event and the user action, what can an admin/operator do first? Are fees segregated from user-share accounting? *Test*: race the privileged tx into the user's claim window.
- **lifecycle-deploy-window** — *Challenge*: deployment/migration will be executed correctly and atomically. *Signals*: init not atomic with first liquidity, public upgrade paths on factories/implementations, ownership handover gaps, migrations breaking dependents, pools/pairs created at launch, post-audit diffs and upgrades. *Ask*: who owns the contracts one block after the deploy script? Do all create/migrate paths enforce the same policy? What breaks in dependents when a dependency migrates or a registry entry is removed? *Test*: front-run the init; pre-create the pool; review every line the upgrade/migration touched — launches, migrations, and graduations are where real losses cluster.
- **offchain-ui-boundary** — *Challenge*: the offchain layer faithfully represents what the user consented to. *Signals*: wallet/snap RPC methods with signing capability, proxies forwarding headers verbatim, circuits/parsers consuming real-world formats with multiple valid encodings, trusted APIs and email/DKIM infrastructure. *Ask*: which consent steps can a connected app skip silently? Does the verifier accept every encoding the external spec permits? *Test*: malicious dapp/snap flows; alternate-but-valid encodings of the attested data.
- **cached-system-of-record** — *Challenge*: our mirror equals the external system's current state. *Signals*: cached signer/owner/approval counts, mirrored voting power, hardcoded addresses of upgradeable dependencies, token addresses vs migrations. *Ask*: where is the reconcile path when the external system of record changes out-of-band? *Test*: change the external system (owner set, token contract, rate) → find every stale mirror and its consequence.

## Audit workflow

1. **Inventory external dependencies.** List every: external call target, oracle/rate read, accepted token (collateral, deposit, reward), integrated protocol, privileged role, keeper/relayer/bridge, and offchain input. Include out-of-scope adapters and oracle contracts — they are prime territory.
2. **Map value decision points.** Mark where prices, rates, balances, or external state decide payouts: mint, redeem, borrow, liquidate, settle, distribute, withdraw.
3. **Cross-product and challenge.** For each dependency × decision point: state what the code believes about that external system, find the matching pattern cards above, and note the card's signals present.
4. **Generate hypotheses.** For each signal match, write a one-line hypothesis: *attacker does X to external system Y, making decision Z pay out wrong*. Prefer chains where one manipulation feeds multiple decisions.
5. **Assess each hypothesis** with the rubric below. Compute cost-to-trigger vs extractable value. Drop only what fails on evidence, not on intuition.
6. **Audit the lifecycle dimension.** Deployment/init window, config surface, upgrade/migration paths, per-chain differences, post-audit diffs. Losses cluster at launches, migrations, and listings.
7. **Attack the defenses.** For each mitigation present (TWAP, sanity bounds, guards, caps, min-shares, cooldowns), test it under the exact attack it was designed for — mitigations create their own surface.
8. **Write up with preconditions.** State the external precondition, the assumption violated, the attack path (atomic or not), the cost, and who bears the loss — not just the buggy line.

## Hypothesis assessment rubric

Score every hypothesis on six axes before ranking:

- **Protocol impact** — what breaks: direct theft, bad debt/insolvency, frozen funds/exit-path DoS, value leakage, griefing. Whose loss: treasury, LPs/lenders, specific users. Size by protocol exposure, not attacker gain. Treat permanent exit-path DoS as ≈ loss for volatile assets.
- **Attacker profitability** — extractable value per run minus costs (swap fees, donation, capital lockup, gas). Repeatable? `tolerance > fee` ⇒ extractable loop; compute iterations-to-insolvency. Profit may be indirect (griefing → later bad debt, cheap collateral).
- **Capital required** — none (config/timing/permissionless call) < dust (griefing) < flash-loanable (temporary, zero risk, repaid in-tx) < funded persistent (defeats TWAP; implies traceable funding) < whale. Capital is rarely the binding constraint; check "none" and "flash" first.
- **Privileges required** — anyone / position owner / semi-trusted (keeper, operator, voter) / single privileged role / governance. Most severe findings are permissionless; insider paths often carry the largest single losses.
- **External preconditions** — market state (low liquidity, depeg, volatility spike), system existence (lending market, AMM pool, keeper set), timing window (epoch, deployment, oracle update, listing), chain condition (congestion, reorg, sequencer downtime). Name each precondition explicitly; "requires X to exist" still counts if X is plausibly coming (a lending market for the token).
- **Atomicity** — single-tx (flash-loanable, MEV-amenable, zero-risk) vs multi-step (spans blocks/reports/settlements; survives private mempools; exploits process latency, not ordering). Evaluate every hypothesis first as single-tx with infinite temporary capital, then as multi-block funded.

Severity heuristics: single-tx + permissionless + no-capital + direct loss ⇒ critical. Multi-step + funded capital + solvency impact ⇒ still high — do not downgrade for "needs capital". No direct profit (griefing, DoS) ≠ safe: compute cost-to-attack vs funds endangered. "Liquidators/keepers will handle it" and "arbers will fix the price" are hypotheses to test, not defenses.

## Final checklist

- [ ] Every price/rate/balance input traced to its ultimate source; cost-to-manipulate each source < value it secures?
- [ ] No spot-price, single-block, or single-source read gates a value decision; TWAP windows ≫ block time with liveness assumptions stated?
- [ ] Oracle writes authenticated; quorum = distinct entities; freshness validated per feed heartbeat; failure mode per feed mapped (manipulation *and* DoS)?
- [ ] No hardcoded peg/parity/1:1 for any pegged, wrapped, or derivative asset; depeg circuit breaker; forced-exit value considered?
- [ ] Units, decimals, and orientation verified for every cross-boundary amount; deposit is the exact inverse of redeem under extreme values?
- [ ] Share price immunized to donations and first-deposit (dead shares/virtual offset/atomic seeding); caps enforced on all transfer paths?
- [ ] Internal ledger reconciled with raw balances (pending liabilities, donations, selfdestruct, skim/sweep)?
- [ ] Every accepted token's mechanics enumerated (fees, rebase, hooks, blacklists, decimals, upgradeability) and survived?
- [ ] Every balance/threshold/vote gate re-checked against one-block borrowed capital and against a future lending market for the token?
- [ ] Every reward/fee/penalty distribution checked for JIT entry-exit and accrual replay (free triggers, zero-value ops)?
- [ ] Every two-step/queued/epoch flow: steps bound together, inputs frozen at step one, third-party "on-behalf" calls harmless, completion restricted?
- [ ] Liquidations: incentive ≥ cost when underwater, denial/evasion impossible for dust, liquidator solvency checked post-trade?
- [ ] Failure, retry, recovery, and migration paths re-apply all happy-path validation and replay protection?
- [ ] Every external address validated against canonical registries; every `to.call(data)` target and approval spender constrained?
- [ ] Cross-chain: endpoint symmetry at boundaries, identity/aliasing resolved, finality depth assumed, message fees/refunds handled?
- [ ] Each external privileged actor (multisig, keeper, relayer, oracle, admin) modeled as compromised — blast radius capped on-chain?
- [ ] Config setters bounded; cross-parameter invariants enforced; recovery tx executable after the worst bad value; config changes simulated against live state?
- [ ] Deployment/migration/listing windows: init atomic, ownership handed over, pools/pairs can't be pre-created, post-audit diffs reviewed?
- [ ] Each mitigation (TWAP, guard, cap, sanity bound, cooldown) re-tested under the exact attack it was built for?
- [ ] Impact sized by protocol exposure; each finding states preconditions, capital, privileges, atomicity, and who bears the loss?
